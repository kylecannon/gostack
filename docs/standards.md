# Standards

General Go style and testing follow
`agentic-harness/.agentic/conventions-go.md`. This file adds only the rules
specific to gostack.

## Code

- **Generated code** lives only in `internal/api/<svc>`. `make gen` runs the
  generator (`codegen/cmd/gostack-codegen`) over the services in `GEN_SERVICES`.
  - Header: `// Code generated by gostack-codegen. DO NOT EDIT.`
  - Never edited by hand. Change the generator or the vendored specs in
    `specs/`, then regenerate.
  - Excluded from lint and format. The exclusion filters reports only; the
    linters still read every file.
  - The generator splits each service's output across several files (types,
    codecs, operations) and never writes one giant file. A single 93k-line
    file costs the `whitespace` linter 16s per lint.
  - Sharded: a file whose declarations run past about 3,000 lines (`maxShardLines`
    in `codegen/cmd/gostack-codegen/emit.go`) becomes `<name>_1.go`,
    `<name>_2.go` and so on, cut at declaration boundaries. `make gen` deletes
    a generated file it no longer writes, so a shard that is no longer needed
    does not linger, and `make gen-check` fails on one that does.
  - A rest service's routing table is checked every time the generator runs: it
    refuses two operations that bind the same request. The per-operation test,
    `Test_routeRules_EveryOperation` in
    `codegen/cmd/gostack-codegen/route_internal_test.go`, sends each rule its
    own request and expects the operation back. It is built on the S3 model
    today, so a second rest service needs its own router builder there first.
- **Handler files.** One file per operation or tight operation group, for
  example `internal/service/sqs/send-message.go`.
- **Unimplemented operations** return 501 through the embedded generated
  `Unimplemented` struct. A handler never fabricates a result to make a test
  pass.
- **AWS errors** are generated typed error values. Handlers return them and the
  gateway serializes them. Handlers never panic. The gateway recovers a panic
  into 500 `InternalError`, or 501 under `FAIL_FAST`. The process keeps
  running.
- **State.**
  - Each service has its own `State`, held in `store.Bundle[State]` keyed by
    account and region. This mirrors `AccountRegionBundle` and
    `CrossRegionAttribute` in `localstack/services/stores.py`.
  - Locks are per shard and per resource. There is no global lock. The one
    exception: a service may hold a single reader-writer lock across its state,
    taken for writing by snapshot, restore and reset and for reading by every
    write (S3's `transfer`), which makes a save wait for writes in flight and
    makes writes wait while the save copies the state; that cost is known and
    recorded in the persistence PR.
  - State types must serialize for persistence.
- **Cross-service calls** (SNS to SQS, Events to Lambda, CloudFormation to
  everything) go through an in-process client that dispatches through the same
  handler chain, so behavior is identical to an external call, as with
  LocalStack's `connect_to`. A service never reaches into another service's
  state.
- **No idle work.** No background goroutine runs while idle. Timers (SQS
  visibility, delays, TTL, persistence flush) are armed on demand from one
  per-service timer heap and stop when it is empty.
- **Hot paths do not use reflection**, and request and response bodies are
  streamed. Never buffer a whole S3 object. Spill to disk above 512 KB, as
  LocalStack's `SpooledTemporaryFile` does.
- **Reflection names a method with a constant.** `reflect.Type.MethodByName`
  takes a string literal; `Type.Method(i)`, `Value.Method` and `MethodByName`
  with a variable make the linker keep every exported method in the binary,
  which cost `bin/gostack` 2.75 MB. Look an operation's method up through the
  generated `OperationMethod`. A lint cannot see a dependency that does it, so
  `Test_gostack_binaryPrunesMethods` in `cmd/gostack` reads the symbols of the
  built binary and fails when methods nothing calls are kept.

## Tests, cheapest first

1. **Unit tests** follow conventions-go.md: table tests, `testify/require`,
   `synctest` for time, `-race` always.
   - A test never asserts on wall-clock time.
   - A test of growth (cost against input size) measures CPU time or counts
     work, decides once on a fixed number of runs, and states in a comment the
     smallest defect it is proven to catch.
2. **Codec conformance.** `scripts/vendor-specs.sh` fetches botocore's
   protocol test fixtures (`tests/unit/protocols/{input,output}/{query,json,rest-xml,rest-json}.json`)
   into `internal/protocol/testdata/botocore` and records them in
   `specs/SOURCES.lock`. Every protocol a codec implements passes them: query,
   json, rest-xml and rest-json so far, and ec2 and cbor as their services
   arrive. Every Smithy trait the codec honors gets its own test.
   aws-emulator's dropped `@timestampFormat` is the cautionary case.
3. **Fuzzing.**
   - `go test -fuzz` on every parser: the protocols, SigV4, aws-chunked, the
     router, the DynamoDB expression grammar, and the JSONata parser.
   - Seed corpora are committed under `testdata/fuzz`.
   - `make fuzz` finds every `Fuzz*` function itself and runs each for
     `FUZZTIME` (default 30s); `make fuzz FUZZTIME=5s` is the quick form.
   - Nightly CI runs each fuzz target for 60s (see Gates).
4. **In-process service tests** use `aws-sdk-go-v2` against an `httptest.Server`
   running the real gateway. They cover only behavior the oracle does not, and
   regressions found in the field. rustack's three fixes are the first cases:
   - DynamoDB `LastEvaluatedKey` when `Limit` ends a page.
   - S3 `Expect: 100-continue` with an empty body.
   - SQS `MessageGroupId` on standard queues.
5. **Parity oracle** (see `architecture.md`). A service change is done when
   its ledger rows move to pass and none regress.
6. **Benchmarks** (below).

## Gates

Pre-commit and CI both run on the toolchain pinned in `go.mod`.

- **Pre-commit** runs `.agentic-quality`, the manifest the harness hook reads:
  `make fmt` on staged `*.go` files, then `make lint`, `make fix-check` and
  `make test` (`go test -race`) on the packages those files belong to. `make -s packages`
  finds those packages, and a failing `go list` fails the rule.
- **`make fix-check`** runs `go fix -diff` and fails on any diff; `make fix`
  applies it. Code uses the newest idiom the pinned toolchain offers, and
  `make fix-check` plus the `modernize` analyzers in golangci-lint enforce it:
  `go fix` follows the toolchain, `modernize` follows the linter's release.
- **CI** (`ci.yml`, on every pull request and every push to main) runs
  `make fmt FMT_ARGS=--diff`, `make tidy-check`, `make gen-check`,
  `make fix-check`, `make lint`, `make test` and `make build`.
- **`make gen-check`** (`ci.yml`) regenerates `internal/api` and fails on any
  modified file or untracked generated file.
- **Parity ledger** (`parity.yml`, on every pull request, and by hand with a
  `services` input) builds an image from GitHub's merge ref, the pull request
  head merged into its base, and runs LocalStack's own tests for the services
  the change touches against it, then `make parity-check`. It compares with
  `HEAD^1`, the base the merge ref was made from, and fails when `HEAD` is not
  a two-parent merge of the pull request head or GitHub reports the pull
  request as not mergeable. A manual run builds the dispatched ref and
  compares with the ledger committed there.
  - Selection is fail-safe: a changed path selects every service in the ledger
    that gostack serves, unless it is one service's own path or cannot change
    the image. gostack serves a service when `internal/service/<svc>/` exists;
    ledger rows do not count. A service with only a LocalStack baseline is never
    selected, by its own files, as a dependent, by `sts` or by a shared path, and
    the manual run's default (`ledger.py services`) leaves it out. A change that
    selects nothing skips every later step of the workflow.
  - A service's own paths are `internal/service/<svc>/` and the generated
    `internal/api/<svc>/` once `internal/service/<svc>/` exists (both also
    select the services whose tests depend on `<svc>`),
    `parity/ledger/<svc>.json`, `parity/exclusions/<svc>.yaml` and
    `cmd/gostack/settings-<svc>.go`, the service's settings mapping. The
    settings file selects `<svc>` and its dependents even for a service whose
    Registration sets a routing hook, since it sets none. A dependent selects
    only once it is served. Every service's tests depend on `sts`, so a change
    there selects every service. The first commit of a service branch that adds
    `internal/service/<svc>/` makes `<svc>` selectable by every rule above.
  - A change under the directories of a service whose Registration sets
    `Mount`, `ClaimHost`, `Claim`, `Fallback` or `Preprocess` selects every
    service: those hooks see requests meant for any service. Today that is
    `s3` and `sqs`.
  - A change to `cmd/gostack/services.go` selects the services its changed
    lines name when every changed line of code is a whole element of the list
    `registrations()` returns or an import of a service's package. Any other
    changed line of code, a `//go:` directive included, selects every
    service. Blank and comment lines name nothing.
  - A `*_test.go` file anywhere, and `LICENSE`, select nothing.
  - `parity/ledger.py` lists the paths that cannot change the image
    (`NO_IMAGE_EFFECT`), the dependencies between services' tests
    (`DEPENDS_ON`) and the services with routing hooks (`ROUTING_REACH`).
    `Test_parityTables` in `cmd/gostack` fails when `ROUTING_REACH` differs
    from the hooks `registrations()` sets, when a package outside
    `internal/service/<svc>/` imports `internal/api/<svc>/`, or when the
    `DEPENDS_ON` keys are not the services whose package imports
    `internal/inproc` or another service's package. Every such service must
    be a key (a caller with no key is a missed selection). A key that is not a
    caller only over-selects, so it passes when it is on `DECLARED_AHEAD` in
    `parity/ledger.py` (`dynamodb`, `dynamodbstreams`, `sns`, `ssm`), and fails
    otherwise; the first commit of a service, its API package imported and no
    in-process call yet, needs no table edit, and a key stays on the list once
    its service calls another. An entry for a service that has a generated
    `internal/api/<svc>` and no `internal/service/<svc>` yet is allowed, so
    the tables are seeded before a service is built; an entry for a service
    with neither fails, as does a registered service, service package or API
    package with no `TEST_DIRS` entry. Which service an in-process call
    reaches and the `sts` entry are reviewed by hand. A service calls
    another service only through `internal/inproc`: the test finds callers by
    that import, so a call made another way (the gateway handler taken through
    `Bind`, an HTTP request to the service's own port) is a dependency it
    cannot see. `Test_settingsFiles`
    holds each `cmd/gostack/settings-<svc>.go` to one declaration, the
    function `<svc>Settings`, used only on a line of `services.go` that names
    the `<svc>` package. `make test` runs both and needs `python3`.
  - `ledger.py check` fails when a ledger holds gostack results for a service
    with no `internal/service/<svc>/` package, since selection no longer runs
    its suite: remove the rows or bring the service back. A directory counts as
    a package only when it holds a non-test `.go` file.
  - On a pull request, the gostack column the run observed for the selected
    services must equal the ledger committed in the merge ref, in either
    direction, or the job fails and names each nodeid. A change commits the
    ledger its run produces, so a fix lands with its row at `pass`.
  - A committed row of a selected service whose test the run did not collect
    (its junit report and the plugin's excluded list) fails the same job and
    is named, unless the row is `excluded` or `parity/demotions.yaml` lists
    it.
  - `docs/parity.md` must equal what `parity/ledger.py` renders from the
    committed ledger; the ledger unit tests check it.
  - A test whose result changes from run to run is excluded with a reason
    and demoted in the same change, never left to flap.
  - A test carrying LocalStack's `requires_in_process` marker is excluded,
    unless `parity/bridgeable.yaml` lists it, which is allowed for two kinds
    only. A `config` test patches nothing but `localstack.config`, which the
    config bridge forwards to the target. An `http-server` test is marked only
    because it starts pytest's `HTTPServer` for the target to deliver to; the
    runner shares the target's network namespace, so the target reaches it on
    localhost. An `http-server` test touches nothing else in the server process
    (no store, no `config.` read, no monkeypatch), and is listed only while the
    LocalStack baseline passes it in the runner. Its note starts with
    `http-server:`; a config note is the variable names.
- **Parity ratchet** (`make parity-check`, in `parity.yml` and in `ci.yml`'s
  `parity-ledger` job, which compare the same merge ref with the same
  `HEAD^1`): a test that is `pass` in the gostack column of the
  ledger at the base stays `pass`. Changing it to `fail`, `skip`, `xfail`,
  `excluded` or null fails the check, and so do removing its row and emptying
  its file. The check names every such nodeid.
  - The one exit is an entry in `parity/demotions.yaml`: the nodeid and a
    one-line reason, reviewed with the change.
  - An entry whose test is `pass` again fails the check until it is removed.
  - `make parity-prune` removes the rows whose test is gone from the pinned
    LocalStack and writes each removed gostack pass there as gone upstream.
    A gone upstream entry whose row is still in the ledger fails the check.
  - A base that names no commit fails the check, and so does the all-zero sha
    unless `HEAD` is the repository's first commit.
  - The localstack column is not under the ratchet. Only its pass to fail
    fails the check, and any other change there is a warning.
  - `make parity-check` first runs the ledger's unit tests
    (`parity/test_*.py`). CI does not run the LocalStack baseline; the
    committed ledger is the baseline. The LocalStack suite comes from the
    commit in `specs/SOURCES.lock`, and the runner image is cached on that sha
    and `parity/runner/`.
- **benchstat** (`bench.yml`, every pull request) compares the micro benchmarks
  on the base and the head with `benchstat` and fails on a regression over 10%
  at p<0.001. It compares only the packages whose test binary changed, in
  shards of one job each, and passes without comparing when none did
  (Benchmarks, "Micro benchmarks").
- **System bench regression** (`bench-system.yml`) runs `bench compare`: a pull
  request's head against its base on the quick profile, and a scheduled or
  manual run against the previous passing run on main with the same profile
  and host fingerprint, which is kept as a workflow artifact.
- **Fuzz** (`fuzz.yml`, nightly and by hand) runs `make fuzz FUZZTIME=60s`, which
  runs every `Fuzz*` function for 60s. A crash uploads the new
  `testdata/fuzz` entries and the log as the `fuzz-crashes` artifact.
- **Linters and formatters** are configured in `.golangci.yml` (v2 format).
  Linting runs in strict mode (`default: all`), and each disabled linter is
  documented there. `govet` runs with every analyzer enabled except
  `fieldalignment`, `exhaustive` treats a `default` case as exhaustive, and
  `gosec` is tuned there. Formatters are gofumpt and gci with two import
  groups.

## Toolchain

The Go version is pinned by the `toolchain` line in `go.mod`, or the `go` line
when there is none. The Makefile derives `GOTOOLCHAIN` from it, stops when both
are missing, and holds the reason for the layout below.

- **Make targets** run under that pin, golangci-lint included. golangci-lint is
  a tool dependency of its own module, `tools/go.mod`, run as
  `go tool -modfile=tools/go.mod golangci-lint`. The product `go.mod` carries
  none of its dependencies.
- **Editors and gopls** do not read the Makefile, so the pin does not reach
  them. Run `export GOTOOLCHAIN=$(make -s toolchain)` in the shell that starts
  the editor. Plain `go` commands outside `make` need it too.
- **Each module** has its own `go mod tidy`. Both `go mod tidy -diff` (root) and
  `go -C tools mod tidy -diff` must exit 0.

## Benchmarks

Every target is a number that gets measured. The first measurement sets the
baseline. After that, CI holds the line.

### Every feature ships its benchmark matrix

A feature is not done until its benchmarks cover the variants it can be called
with. A change that adds or alters a feature adds or updates its rows in the
same PR. A missing row is a review blocker.

| Axis | Values |
|---|---|
| Payload | small (under 1 KiB), medium (about 64 KiB), and the service's maximum |
| Concurrency (system bench) | 1, 16, 64 |
| Wire protocol | every protocol the service speaks (SQS: query and json) |
| Feature options | each option that changes the code path, e.g. SQS standard vs FIFO, single vs batch, short vs long poll, with and without message attributes |
| Persistence | off, and on (`PERSIST_SQS=1`) for services that persist |

Name sub-benchmarks so benchstat lines them up across runs:
`BenchmarkSendMessage/proto=json/queue=fifo/payload=64KiB`. An axis that does
not apply to a feature is left out, not filled with a placeholder.

A micro benchmark's persistence-on rows sit under the same function as its
persistence-off rows, with a `persist=on` key first
(`BenchmarkPutObject/persist=on/payload=1MiB/concurrency=16`) and no key for
off, so the base's rows keep their names. `benchstat -col /persist` sets the two
side by side.

### Micro benchmarks

- Live in `*_benchmark_test.go`, loop with `b.Loop()`, and report bytes with
  `b.SetBytes` where a payload is involved.
- Cover:
  - routing;
  - each protocol codec, decode and encode, across the payload axis;
  - SigV4 parsing;
  - every service operation's handler path, across its matrix.
- benchstat (see Gates) compares ten runs of each benchmark on the base and on
  the PR. A regression over 10% with p<0.001 fails the build unless it is
  accepted (below). benchstat prints p to three decimals, so the gate flags a
  row only when it prints `p=0.000`; the comment at `significance` in
  `bench/gate.go` has the arithmetic.
- The gate measures base and head interleaved, never one tree after the other:
  `make bench-ab` runs ten rounds of one run per tree, alternating which tree
  goes first (base head, head base, ...). A runner that speeds up or slows down
  during the job then moves both sides alike instead of reading as a regression.
- Before each round the gate links both trees' benchmark binaries again, each
  with its own function layout (`-randlayout`, a different seed per tree and
  round), because a change elsewhere in the binary can move where a benchmark's
  functions land, and one fixed layout per tree would read that as a regression
  in code that did not change.
- The gate compares only what can differ. `make bench-select` builds each
  benchmark package's test binary for the base and the head with the gate's
  flags at one layout (no `-randlayout`), plus `-trimpath`, which keeps the
  checkout's path out of the binary, and builds the head a second time with an
  empty build cache:
  - a package whose head binary matches its base binary byte for byte and whose
    files that are not Go source match too (below) cannot regress and is not
    run;
  - a package whose two head builds differ is not reproducible, and runs;
  - a package only the head holds has nothing to compare against. Each of its
    top-level benchmarks runs once at the gate's benchtime, as it will in a
    later comparison, so one that breaks late or runs over the limit below
    fails selection, and none is compared;
  - a package only the base holds is dropped;
  - a package whose test binary lists no benchmark (`-test.list '^Benchmark'`
    prints none) is not a benchmark package, whether the head only, both trees
    or the base only hold it: the grep that picks packages to build also matches
    a `func Benchmark` inside a string literal, so the binary's list decides.
    It is dropped and the summary prints it as `no benchmark`. A list that
    fails (non-zero exit, a crash) fails selection;
  - a top-level benchmark only the head holds, in a package that runs, is
    treated the same way: it runs once at the gate's benchtime and is held to
    the limit below, but is not planned and not compared, so a shard never holds
    it alone.

  The base is the target branch's tip, so a branch behind main also selects the
  packages main changed since it branched.
- A benchmark reads no file at run time. What it needs is built in code or
  embedded, because the test binary does not hold a file the benchmark opens.
  Selection does not check the rule at run time. It hashes every file under a
  package's directory that is not a `.go` file, and every file under a `testdata`
  directory, `.go` ones included, and a change to any of them makes the package
  `changed`, so a benchmark that reads one of those is still compared. The hash
  does not cover, and the rule stands for:
  - a file outside the package directory;
  - a file below a subdirectory that holds a `.go` file of its own, whether that
    is another package (it has a verdict of its own, which the parent's does not
    follow) or a generator the build ignores (`//go:build ignore`), unless the
    subdirectory is itself under a `testdata` directory;
  - a `.go` file outside `testdata` that the build ignores, read as data;
  - a symbolic link's target: the link is hashed by name, so retargeting it is
    not a change.
- Selection times one run of each top-level benchmark of a selected package, and
  of a package or benchmark only the head holds, at the gate's benchtime. It
  packs what is compared into the fewest shards of about 40 minutes
  (`BENCH_SHARD_BUDGET`). A shard's estimate is 5 minutes of setup plus ten
  rounds, each running its benchmarks once per tree and relinking each of its
  packages (1.5 s a package). A package that would overrun that is split by
  top-level benchmark (`-test.bench '^(A|B)$'`). A top-level benchmark whose own
  estimate is past 40 minutes gets a shard of its own, up to what a shard job
  holds, its 60-minute timeout (`BENCH_SHARD_LIMIT`, about 164 s a run). Past
  that, selection fails and names the benchmark and its estimate: its author
  splits it. A benchmark only the head holds is held to the same limit. Each
  shard is a job on its own runner that runs `make bench-ab` with `BENCH_PLAN`
  naming its share, so base and head are always measured on one machine.
- `make bench-ab` without `BENCH_PLAN` still runs every benchmark of both trees.
  With one, it fails when the plan is missing, empty, malformed, or names a
  package a tree holds no benchmark of. A regex that matches no benchmark of its
  package does not fail it; `bench join` does, so a shard cannot measure nothing
  and pass.
- Each matrix entry carries its `index`, from zero, and the shard job names its
  artifact `bench-shard-<index>` from it, not from `strategy.job-index`, whose
  order GitHub does not say follows the entries'.
- The `benchstat` job runs `bench join`, which reads exactly `bench-shard-0` to
  `bench-shard-<n-1>` of select's matrix, however many `bench-shard-*` artifacts
  the run holds (a re-run keeps those of the attempt before). It fails when one
  of them is missing, or when the base or the head output of a shard has no
  rows for a package and regex of that shard's plan. It then runs benchstat once
  and `bench gate`, and fails when selection or any shard did not succeed.

### System bench (`bench/`)

The same workload runs against `gostack:latest`, `gostack:slim` and the
LocalStack image. Measured:

- time from container start to `Ready.`;
- idle RSS, and idle CPU over 60s (target: no wakeups), with the image
  HEALTHCHECK on and off;
- RSS and CPU under load;
- p50 and p99 per operation for each cell of the feature matrix;
- image size.

An "agentic" workload runs many short create, use and delete cycles across
every implemented service. Results are committed to
`bench/results/<date>-<sha>.json` as human records. `go run ./bench compare`
checks a run against the newest committed result with the same host
fingerprint and fails when a gostack cell regresses past its threshold;
`make bench-system` runs it after measuring. CI never compares against the
committed files, because a runner never has the fingerprint of the machine
they came from: the scheduled run compares with the artifact the previous
passing run on main uploaded. LocalStack cells are reference numbers and never
gate. A latency also has to rise by 0.05 ms (p50) or 0.5 ms (p99) to regress,
so a tick of the 0.01 ms resolution at c=1 cannot fail the gate.

A run is a measurement only while its target works. After every run the
orchestrator checks that the target container is still running; a run whose
container exited or was removed fails, and is recorded in the cell's
`failed_runs` instead of being dropped, so a side never ends with fewer runs
than the other unrecorded. An operation that reports errors is recorded with its
count in the result file's `problems`. `bench compare` fails when the head has a
problem the base does not: an operation with errors where the base has none, a
cell with failed runs or no completed run where the base ran, a measurement the
head could not take of a kind (the text before the first `:` of its line) that the
base did not also fail to take, or any of these in a cell only the head has. It also fails when the
head has more failed runs in a cell than the base, or operation errors in the
same cell and operation that are at least 10 and more than 10 times the base's,
and when the head lacks a gated target, or a cell the base completed, that it
was asked to measure ("missing from the head"; a different profile, a service
the head did not select, or a cell the head's matrix no longer has, listed as
"removed from the matrix", is not asked). A cell with no completed run in a
result that predates `failed_runs` counts as having failed every run its reps
asked for. Each row prints the cell, the operation
and both counts. Any other problem on both sides is listed and does not fail,
and neither do cells with unequal run counts. Zero tolerance for an error only
the head has is deliberate: the committed results hold 0 errors in over 900,000
operations, a stray error costs one rerun, and a floor would let a rare race
through. A regression computed from fewer runs than the run asked for says so in
its row ("head 4 of 5 runs"). The accepted list does not cover any of this.
Containers are removed with their volume (`docker rm -f -v`), and `-out` and
`-base-out` are compared as absolute paths with their links resolved.

A pull request measures its base and head images in one run,
`bench run -base-image`, never one image after the other. Every repeated
measurement (each startup and idle run, and each run of a cell) alternates the
two images and flips which goes first each time: base head, head base, ....
A runner that slows down during the job then moves both sides alike, as in the
micro-benchmark gate.

The pull-request comparison runs each cell five times a side (`-reps 5`), not
the default three. A metric fails only when the two sides' ranges do not
overlap, and pure noise puts them apart once in C(6,3) = 20 orderings at three
runs a side, once in C(10,5) = 252 at five.

### Accepted regressions

A regression accepted as the cost of a change is listed in
`bench/accepted.yaml`, in the pull request that brings it, with its metric,
the largest change accepted, a one-line reason, the pull request and a commit
that carries the cost. Both CI gates read the file and print what it holds
under "Accepted". A listed metric past its bound, and every unlisted one, still
fails. A bound is a finite number above zero with at most one leading `+`, as
`+50%` or, for a system metric, `6 MiB` (units `MiB`, `ms`, `s`, `cycles/s`).
A percent is at most 1000%. An absolute value is at most 65536 `MiB`, 3600000
`ms`, 3600 `s` or 10000000 `cycles/s`. A percent bound reads as a rise in what
the work costs, so a throughput (a `/s` unit, `cycles/s`) that falls d percent
counts as a rise of 100d/(100-d) percent: `+100%` lets a latency double and a
throughput halve, `+1000%` stops at a drop to an eleventh, and a throughput that
falls to nothing, or a cost that rises from a base of zero, is past every
bound. Neither prints a percent, so each gate finds them another way. `bench
gate` reads the `?` change benchstat prints for a cost whose base is zero. It
reads no row for a throughput that falls to zero, because benchstat sets each
file's figure in a table of its own (the head's unit becomes `MB/s`); the
benchmark's `sec/op` row catches it instead, a rise past the 1000% cap that no
entry can hold. The system compare fails a throughput whose head median is
zero against a measured base, even when one run of the head ran at the base's
rate. A refusal states the rise it computed (an 18% fall under `+20%` reads "a
rise of +22.0% in cost"). An absolute bound is the worst head value, a ceiling
for a cost and a floor for a throughput, and is held to the same 1000% cap: a
pair whose change the bound allows past 1000% fails, so
`65536 MiB` accepts no more than `1000%` does. An infinite, negative, zero,
repeated-sign or over-cap bound is a load error, as is a second YAML document
and a second entry that can match the same row as another: one metric, or a
benchmark `X` with `X-<digits>` (`RouteDetect/host` and `RouteDetect/host-2`
both match the row `RouteDetect/host-2`). A benchmark whose own name ends in
`-<digits>` is listed alone without trouble. A list with no entries is valid.
An entry's `package` is the full import path or the path below the module
(`internal/route`). Names compare exactly, so a glob or a trailing space in an
entry matches nothing. A bound at or under what the gate flags holds nothing
either: a benchstat cost is flagged past a rise of 10%, so `+10%` holds none, and
a throughput past a fall of 10% (a rise of 11.11% in cost), so `+11.11%` holds
none; the system gate flags a metric past its own limit (its output lists them).
Both gates print such an entry, and an entry that matched no regression, quoted
and with the reason, under "Unused accepted entries", even when nothing
compares, and do not fail on them.

An entry applies only while the head holds its commit and the base does not, so
it expires once main holds the commit. The pull request lands with a merge
commit, never a squash: a squash or rebase merge leaves the commit out of main,
so the entry never expires. Delete the entries in the first change after the
merge.

A result file is schema 3. A cell id is `<service>/<workload>/<options...>`,
such as `sqs/messaging/persist=off/payload=256B/queue=standard/shape=single/proto=json/c=16`.
A cell holds its operations as a map from name to latency, and declares the
environment variable that turns its persistence on. A service is added by
registering a workload in `bench/` (`Service`, `Name`, `Ops`, `Cells`, `Run`);
the report and the compare gate read the operations from the result and name
none. A file of schema 2 is converted when it is loaded.

### Runtime knobs

- Services start lazily on first request. `EAGER_SERVICE_LOADING` is honored.
- `GOMEMLIMIT` is honored, and Go is container-aware about `GOMAXPROCS`.
- Buffers come from `sync.Pool`.
- pprof is served only when `DEBUG=1` (path in `architecture.md`).
